# Гайд: як тестувати побудову глосарію з тексту

Стосується M1 з `docs/PIPELINE_ROADMAP.md` — універсального шляху, який працює
**на будь-якому проєкті**: без скрипта, без вихідного коду гри, без вікі. Потрібен лише
відкритий проєкт із текстом і налаштована AI-модель.

---

## 0. Перед початком

### Де насправді лежить глосарій

**Глосарій НЕ лежить біля проєкту.** Він прив'язаний до **плагіна**, а не до проєкту, і
живе всередині теки програми. Порядок пошуку
([`_resolve_glossary_path`](../handlers/translation/glossary_prompt_manager.py)):

1. `plugins/<плагін>/translation_prompts/glossary.{json,md}`
2. `plugins/common/defaults/glossary.{json,md}`
3. `translation_prompts/glossary.{json,md}` — глобальний фолбек

Якщо на рівні є і `.json`, і `.md`, береться **новіший за часом зміни**.

**Наслідки, які легко проґавити:**

- **перестворення проєкту не очищає глосарій** — він переживає проєкт;
- у плагінів `plain_text`, `zelda_mc`, `zelda_ww` є власний `glossary.md`, а от у
  **`zelda_bmg` (Twilight Princess) власного немає**, тож він падає аж на глобальний
  `translation_prompts/glossary.json`;
- цей глобальний файл **спільний** для всіх плагінів без власного глосарію: два різні
  проєкти на таких плагінах писатимуть в один файл.

### Кроки

1. **Зроби копію глосарію** — того файлу, який знайдено за списком вище. Пайплайн пише
   саме в нього; копія — це шлях відкату.
2. **Щоб почати з чистого аркуша** (рекомендовано для експерименту): або перейменуй
   знайдений файл, або створи для плагіна власний порожній:

   ```bash
   mkdir -p plugins/<плагін>/translation_prompts && echo "[]" > plugins/<плагін>/translation_prompts/glossary.json
   ```

   Другий варіант кращий: він і дає чистий старт, і **прибирає плагін зі спільного
   глобального файлу** назавжди.
2. **Перевір модель.** Settings → AI Translation: провайдер і ключ. Побудова використовує
   ту саму конфігурацію, що й наявна дія «AI Build Glossary» для блоку.
3. **Для першого прогону візьми один блок**, а не весь проєкт. Один блок — це десятки
   викликів, весь проєкт — тисячі.

Запуск: **Tools → Build Glossary from Text…**

---

## 1. Найкоротший розумний тест (5 хвилин)

**Налаштування:** Area = `Current block`, Depth = `Draft (fast, rough)`,
Chunk size = за моделлю (локальна → Local, хмарна → Cloud), «Also propose translations» = ☐.

**Що має статися:**
- діалог прогресу показує етапи `Sweep 1/N`, далі `Seed …`;
- у кінці — вікно «Finished: seeded N, described 0, translated 0».

**Що перевірити в глосарії:**
- з'явилися нові записи;
- у кожного є **опис**, але **перекладу немає** (порожньо);
- секції лише з п'яти дозволених: `Characters`, `Items`, `Places`, `Boss Names`, `Terms`.

> `described 0` тут **правильно**. Чернетковий режим не робить прохід опису — опис у
> записах узятий із самого обходу.

---

## 2. Ретельний режим — головна перевірка (те, для чого все робилося)

**Налаштування:** Area = `Current block`, Depth = `Thorough`, translate = ☐.

**Що має статися:** етапи `Sweep → Seed → Describe`, у кінці
«seeded N, described M, translated 0».

**Що перевірити:**
- описи **змістовніші**, ніж у чернетці: вони будуються з контексту навколо **кожного**
  входження терміна, а не з одного випадкового місця;
- переклад досі порожній — так задумано, він окремою фазою.

**Ключовий тест якості.** Знайди термін-пастку — слово, що має неочевидний сенс саме в
цій грі (класика: `Spring Goron`, де `spring` — купальня/джерело, а не пора року).
Порівняй його опис у чернетковому й ретельному режимах: ретельний має спиратися на
справжній сенс. Якщо він теж помиляється — це сигнал, що моделі не вистачає контексту,
і ось тут перевір, чи не варто взяти більшу модель.

---

## 3. Переклад (фаза 3)

Постав ☑ «Also propose translations now» і прогони ретельний режим (або чернетковий).

**Що перевірити:**
- у записів з'явився переклад;
- переклад **узгоджений з описом** — саме тому фаза йде після опису;
- у неоднозначних термінів **кілька варіантів** із обґрунтуванням;
- у звичайних термінів — **один** варіант. Якщо варіанти масово по 3 на кожен нудний
  топонім, це баг: сигнал «має варіанти» має бути рідким і значущим.

---

## 4. Доповнення — режим, що врятує чернетку

Це відповідь на «я вже прогнав чернетку, невже все наново?».

**Як перевірити:**
1. прогони `Draft` на блоці;
2. далі на **тому самому** блоці — `Augment existing entries`.

**Що має статися:**
- у результаті **`seeded 0`** — доповнення нічого не засіює;
- **`described N` > 0** — воно описує вже наявні записи;
- **обходу тексту немає** (етап `Sweep` не з'являється, і це видно за швидкістю).

Так само працює для записів, доданих руками або з інших джерел.

---

## 5. Скасування й безпека даних

**Скасування:** запусти ретельний режим на великому блоці й натисни Cancel у діалозі
прогресу. Очікування: зупиняється швидко, повідомляє «(cancelled)», **уже зроблене
зберігається**, програма не зависає.

**Найважливіша перевірка безпеки — чужі записи не псуються:**
1. додай руками запис із перекладом, який тобі дорогий;
2. прогони будь-який режим на блоці, де цей термін зустрічається;
3. **переклад і опис мають лишитися недоторканими.** Пайплайн заповнює прогалини,
   а не перезаписує вирішене.

## 6. Область (Area)

| Вибір | Що бере | Коли |
|---|---|---|
| `Current block` | активний блок | завжди починай звідси |
| `Selected blocks` | виділені в дереві (неактивно, якщо нічого не виділено) | середній прогін |
| `Whole project` | усі блоки | лише коли впевнений у моделі й ціні |

## 7. Розмір чанка

| Пресет | Символів | Для кого |
|---|---|---|
| Local / small | 2000 | локальні моделі (Gemma тощо) |
| Balanced | 4000 | типово |
| Cloud / large | 8000 | великі хмарні моделі |

Симптом «завеликий чанк» — модель **пропускає** очевидні терміни або віддає зламаний JSON.
Візьми менший пресет. Тут потрібна вичерпність переліку, а не глибина — ширший вхід її псує.

---

## 8. Чого очікувати на іншому проєкті (не Twilight Princess)

Цей механізм **не знає нічого про гру**, тому переноситься без змін. На плагіні без
жодних додаткових можливостей ти отримаєш той самий результат: обхід тексту → терміни →
описи → переклади.

Різниця лише в тому, що плагін TP додатково постачає метадані рядка (тип вікна, роль
вмісту), які потрапляють у промпт і уточнюють класифікацію. Плагін без них просто не дасть
цієї підказки — і це передбачено, а не поламано.

**Тест переносності:** прогони чернетковий режим на проєкті з `plain_text` або іншим
плагіном. Очікування: працює, секції ті самі п'ять, описи є.

## 9. Коли щось не так

| Симптом | Причина / що робити |
|---|---|
| «Open a project first» | проєкт не відкритий |
| «Failed to initialize AI provider» | немає ключа/моделі в Settings → AI Translation |
| Записів дуже мало | модель занадто мала для екстракції, або чанк завеликий |
| Зламаний JSON у логах | зменш чанк; парсер терпить огорожі й зайву прозу, але не будь-що |
| Записи не з'явилися в UI | глосарій зберігається й підсвітка оновлюється в кінці; глянь `app_debug.txt` |
| «Звідки взялися чужі записи?» | глосарій прив'язаний до плагіна, а не до проєкту (розділ 0). Новий проєкт успадковує наявний глосарій плагіна |
| Секції не з тих п'яти | старі записи з попередніх прогонів «AI Build Glossary» мають довільні секції (`Locations`, `Equipment`, `Consumables`…). Фіксована таксономія діє лише для нових записів |
| Дуже довго | нормально: обхід послідовний. Почни з одного блоку |

Логи: `app_debug.txt` (усі AI-запити й відповіді теж туди).

## 10. Що **не** входить у цей етап

Щоб не шукати те, чого ще нема:

- **структурний засів із даних гри** (готові предмети/місця/боси) — M3;
- **зовнішній лор (вікі)** як джерело опису — M3 (зараз вікі-пошук лише в профайлері
  персонажів, окремим механізмом);
- **адресат репліки** — M4;
- **жовта підсвітка непідтверджених** у вікні глосарію — статус і варіанти вже
  зберігаються в даних, але UI-підсвітка ще не намальована (M2);
- **майстер-провідник** — M5.
