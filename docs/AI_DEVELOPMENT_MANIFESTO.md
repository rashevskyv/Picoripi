# AI Development Manifesto For Picoripi

This manifesto defines how AI agents should develop Picoripi. It is intentionally practical: every rule should help preserve correctness, performance, user trust, and long-term maintainability.

Picoripi is now largely AI-developed, so the AI must behave less like a code generator and more like a careful maintainer with architectural memory.

## 1. Core Principles

### 1.1. Protect User Work First

- Never overwrite or revert unrelated local changes.
- Always inspect `git status --short` before broad edits.
- Treat unknown modified files as user work unless there is clear evidence they were generated by your own current task.
- Preserve project data, session files, plugin data, glossary files, and translation files with migration paths.
- Do not remove old behavior unless the replacement is implemented, tested, documented, and compatible with existing projects.

### 1.2. Prefer Small, Verified Steps

- Make the smallest change that fully solves the problem.
- Prefer a focused fix plus regression test over a broad rewrite.
- Decompose large modules only around stable contracts and existing tests.
- Keep changes local to the ownership boundary implied by the bug or feature.
- After every meaningful change, verify the relevant path before moving on.

### 1.3. Respect The Existing Architecture

- Read nearby code before editing.
- Follow local naming, structure, error handling, and Qt signal patterns.
- Prefer existing services and helpers over new abstractions.
- Add new abstractions only when they remove real duplication or isolate a risky lifecycle boundary.
- Keep product code free of test-specific checks such as mock detection.

### 1.4. UI Must Stay Responsive

- Never add synchronous disk, network, AI, SQLite, archive parsing, or heavy computation to the UI thread.
- Use `QThread`, timers, chunking, or time-slicing for long work.
- Provide cancel paths, timeout paths, and visible progress or status feedback.
- Avoid `QCoreApplication.processEvents()` in production paths unless a document explains why no safer option exists.
- Do not block shutdown on long waits from UI callbacks.

### 1.5. Tests Are Product Infrastructure

- Tests are not a formality. They are part of the architecture.
- Any bug fix needs a regression test unless the change is documentation-only or truly untestable.
- Any new async worker needs lifecycle coverage.
- Any performance fix needs either a deterministic performance test or a clearly documented measurement.
- Test helpers must model real contracts, not patch global Python or Qt behavior.

## 2. Required AI Workflow

Every AI coding session should follow this sequence unless the user explicitly asks only for analysis.

1. Inspect the current state.
   - Run `git status --short`.
   - Identify modified files that are likely user changes.
   - Read the relevant local code before forming a final plan.

2. Understand the ownership boundary.
   - Is the change in `core/`, `handlers/`, `ui/`, `components/`, `plugins/`, or `tests/`?
   - Which existing service owns the behavior?
   - Which tests already cover it?

3. Implement narrowly.
   - Avoid opportunistic refactors.
   - Keep compatibility adapters where callers still depend on old contracts.
   - Preserve user-facing behavior unless the request is explicitly to change it.

4. Add or update tests.
   - Use focused unit tests for pure logic.
   - Use `pytest-qt` smoke tests for real Qt lifecycles.
   - Use performance tests for latency-sensitive paths.
   - Run tests in parallel by default.

5. Update documentation.
   - Update `docs/FEATURE_REFERENCE.md` for important user-facing behavior.
   - Update `docs/TESTING_STRATEGY_AND_AUDIT.md` for test policy or test infrastructure changes.
   - Update `docs/PLUGIN_AUTHORING_GUIDE.md` and `plugins/default_plugin/` when plugin contracts change.
   - Update `AUDIT.md` for audit findings, completed improvements, and active follow-ups.

6. Verify and report.
   - Run the narrowest relevant test first.
   - Run `test_all.ps1` for release-level verification or broad changes.
   - Run `git diff --check`.
   - Report what changed, what was verified, and what remains risky.

## 3. Architectural Rules

### 3.1. Data Flow

- `AppDataStore` owns shared state.
- `DataStateProcessor` owns data mutation and save/revert/session operations (delegating to `SessionManager`, `RevertManager`, and `SetCalculator` inside `core/data_processor/`).
- Handlers should not mutate `data`, `edited_data`, block metadata, or unsaved flags directly when a processor API exists.
- UI code should request state changes through handlers/processors and then trigger coordinated UI updates.
- Session persistence must be versioned, validated, and compatible with old data where practical.

### 3.2. MainWindow Boundaries

- `MainWindow` is an orchestrator, not a dumping ground.
- New logic should usually live in a handler, service, updater, or plugin class.
- If a function needs many `mw.*` attributes, consider whether it should receive a narrower context object or data transfer object.
- Use `ProjectContext` style contracts where possible to reduce tight coupling.

### 3.3. UI Updaters

- Updaters should coordinate rendering, not own business rules.
- Filtering, problem aggregation, and data queries belong in dedicated query services such as `FilterQueryAPI`.
- Rendering-heavy preview work must be lazy, cached, chunked, or time-sliced.
- Tree state restoration must tolerate missing items and stale selections.

### 3.4. Plugins

- Plugin-specific behavior belongs in plugin modules, not scattered through core UI code.
- New plugin behavior should start from `plugins/default_plugin/`.
- Shared rules belong in `plugins/common/problem_rules/`.
- Plugin contracts must be documented in `docs/PLUGIN_AUTHORING_GUIDE.md`.
- Any change to plugin loading, config discovery, save/load contracts, font maps, tags, or rule execution should update the default plugin tests.

### 3.5. AI And Network Features

- AI calls must be asynchronous and cancellable.
- Never perform provider calls in constructors or direct UI event handlers.
- Provider errors must surface as user-visible error states, not silent failures.
- Prompt construction should be deterministic and testable.
- Caches must include invalidation keys for plugin, file path, settings, prompt version, model/provider, or source data when relevant.

### 3.6. Persistence And File I/O

- Prefer explicit, validated, human-readable formats for durable state.
- Use atomic writes for durable files.
- Use temporary files and cleanup on failure.
- Never load unsafe formats from untrusted paths without a strong reason and clear boundary.
- Avoid disk writes from fallback UI/test paths unless the write target is explicit and temporary.

## 4. PyQt Lifecycle Rules

### 4.1. QThread And Worker Ownership

- Every worker/thread pair needs a clear owner.
- Connect `finished` to cleanup paths such as `deleteLater()` where appropriate.
- Provide cooperative cancellation.
- Avoid `terminate()` except as an explicit diagnostic fallback.
- Do not call long blocking `wait()` from active UI event handling unless shutdown semantics require it and the timeout is bounded.
- Real-thread tests must always stop and wait for OS-level thread completion.

### 4.2. QTimer And Deferred Work

- Use instance-owned timers when deferred work must be cancellable.
- Avoid static `QTimer.singleShot(...)` for work that can outlive a project, dialog, or owner.
- Cancel timers during project close, dialog close, and handler teardown.
- Time-slice expensive timer work with a clear budget.

### 4.3. Qt Object Lifetime

- Treat deleted Qt wrappers as a real production risk.
- Check object ownership and parent relationships when widgets, dialogs, highlighters, or workers outlive their creator.
- Avoid storing long-lived references to widgets that can be destroyed independently.
- Prefer signal disconnection or owner-level cancellation during teardown.

## 5. Performance Rules

### 5.1. Hot Paths

Be especially careful around:

- preview rendering and filtering;
- block tree updates;
- text width calculation;
- syntax highlighting;
- glossary matching;
- spellchecking;
- AI prompt context lookup;
- archive parsing/compression;
- session save/restore;
- MemePalace mapping and database queries.

### 5.2. Required Performance Habits

- Avoid repeated full-project scans inside paint/update loops.
- Cache only when invalidation is clear.
- Prefer indexed lookups for repeated filter/search/glossary operations.
- Batch UI updates where possible.
- Use lazy loading for large previews and large trees.
- Time-slice background pre-caching.
- Add deterministic performance tests for any optimization that protects a known latency budget.

### 5.3. Performance Budgets

- UI input should not visibly lag during normal typing.
- Preview/background caching should yield frequently.
- Tests marked `performance` should stay deterministic, local, and independent of network or machine-specific external tools.
- If a test has a timing budget, document the dataset size and why the threshold is meaningful.

## 6. Testing Manifesto

### 6.1. Default Commands

Run the comprehensive verification script for broad changes:

```powershell
powershell -ExecutionPolicy Bypass -File .\test_all.ps1
```

Run the default suite in parallel:

```powershell
$env:PYTHONPATH = "."; .\venv\Scripts\python.exe -m pytest -n auto tests/
```

Run performance tests explicitly:

```powershell
$env:PYTHONPATH = "."; .\venv\Scripts\python.exe -m pytest -n auto -m performance tests/test_performance.py
```

Run linting:

```powershell
$env:PYTHONPATH = "."; .\venv\Scripts\python.exe -m ruff check .
```

### 6.2. Test Selection Rules

- For pure logic: add small unit tests near the owning subsystem.
- For handlers: test state transitions, side effects, error paths, and UI updater calls.
- For updaters: test data selection and rendering coordination without relying on fragile pixel-perfect GUI assertions.
- For workers: add at least one real lifecycle test with start, signal, cancel/finish, and cleanup.
- For persistence: test roundtrip, corrupt input, old-version input, and failed write/replace.
- For plugins: test load/save roundtrip, tag handling, width behavior, problem detection, and auto-fix contracts.
- For AI features: test prompt construction and response handling with fake providers, not real network calls.

### 6.3. Mocking Rules

- Do not monkeypatch global `Mock`, `MagicMock`, Python builtins, or Qt classes globally.
- Use explicit fake objects for domain contracts.
- Use `MagicMock` only at the boundary where call observation is the point of the test.
- Product code must never import or check `unittest.mock`.
- Avoid product-code branches like `if this_is_a_mock`.
- If a test needs special fallback behavior, put it in the fixture, fake, or local test helper.

### 6.4. Qt Test Rules

- Prefer `pytest-qt` for real signal/lifecycle behavior.
- Avoid fixed sleeps when `qtbot.waitSignal` or `qtbot.waitUntil` can express the condition.
- If using `qtbot.waitUntil`, make the predicate observable and deterministic.
- Always clean up real workers and timers in `finally`.
- Do not leave QThreads running at test exit.
- Avoid sharing mutable Qt objects across `pytest-xdist` workers.

### 6.5. Regression Test Rules

Every bug fix should answer:

- What failed before?
- Which test would have caught it?
- Does the test fail without the fix?
- Does the test cover the risky edge, not just the happy path?

If the answer is unclear, improve the test before declaring the bug fixed.

## 7. Documentation Rules

### 7.1. Documentation Is Part Of Done

A change is not complete if it changes user workflows, plugin contracts, AI behavior, test policy, or release process without updating the relevant docs.

Update:

- `README.md` for top-level project map and common commands.
- `GEMINI.md` for AI-facing working context.
- `AUDIT.md` for audit status, completed improvements, and active TODOs.
- `CHANGELOG.md` for release notes.
- `docs/FEATURE_REFERENCE.md` for user-facing features.
- `docs/TESTING_STRATEGY_AND_AUDIT.md` for test strategy.
- `docs/PLUGIN_AUTHORING_GUIDE.md` for plugin authoring.
- `plugins/default_plugin/README.md` for template-specific plugin instructions.

### 7.2. Documentation Quality Rules

- Prefer concrete commands and file paths.
- Document current behavior, not desired behavior.
- Mark future work explicitly as future work.
- Do not leave stale version numbers or stale PyQt versions.
- Keep docs synchronized with tests.

## 8. Release And Versioning Rules

- When the user asks to commit/release, bump the version.
- Update `utils/constants.py`, `README.md`, `GEMINI.md`, `AUDIT.md`, and `CHANGELOG.md`.
- Run `test_all.ps1` before release.
- Confirm that docs mention important behavior changes.
- Do not tag a release if tests are failing unless the user explicitly requests a known-broken tag.

## 9. AI Agent Self-Checklist

Before editing:

- Did I inspect `git status --short`?
- Did I read the relevant local code?
- Do I know which module owns the behavior?
- Am I preserving unrelated user changes?

Before finishing:

- Did I add or update tests for changed behavior?
- Did I run the relevant parallel tests?
- Did I update the relevant docs?
- Did I run `git diff --check`?
- Did I report remaining risks honestly?

## 10. What Good AI Development Looks Like Here

Good AI development in Picoripi is not just fast code output. It is careful stewardship:

- small changes that fit the existing system;
- high confidence from targeted and parallel tests;
- respect for PyQt lifecycles;
- no hidden UI freezes;
- no hidden data loss;
- no product-code test hacks;
- clear docs that help the next AI continue without rediscovering everything.

The goal is not only to make Picoripi work today. The goal is to make the next correct change easier.
