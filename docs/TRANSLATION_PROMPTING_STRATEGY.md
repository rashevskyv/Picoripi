# Стратегія промптінгу та контекстного перекладу

> Версія: чернетка 1.0 · Цільова модель: **Gemini 3 Flash** (із сумісністю для Claude / OpenAI / Ollama)
> Статус: проєктний документ. Описує **цільову** архітектуру + перелік змін, які треба внести в код.

Цей документ — єдине джерело правди про те, **як Picoripi постачає штучному інтелекту контекст для перекладу** і **як підготувати зовнішній сценарій гри** так, щоб його можна було переносити з плагіна на плагін без переписування коду.

Головна теза: **переклад настільки хороший, наскільки багатий і структурований контекст**. Тому система будується навколо одного канонічного артефакту — *підготовленого сценарію* — з якого детерміновано виводиться все інше (хто говорить, де, у якому порядку, з ким, у якому тоні).

---

## 1. Принципи

1. **Максимум контексту на рядок.** Кожен рядок перекладу повинен нести зі собою: хто говорить, до кого, у якій сцені, що відбувається візуально, які стосунки між персонажами, які терміни глосарія застосовні, що було сказано до і після.
2. **Один канонічний артефакт.** Сирий walkthrough (GameFAQs `.txt`) — ненадійне джерело. Ми один раз конвертуємо його в **канонічний Markdown-сценарій** із чіткою схемою. Усі наступні етапи читають тільки його.
3. **Детермінізм над евристикою.** Там, де зараз працює нечіткий пошук по «дистильованому» тексту, канонічний формат дає прямі ID-прив'язки. ШІ використовується для *збагачення* (опис персонажа, опис сцени), а не для *структурування*.
4. **Промпти — це дані, а не код.** Усі промпти живуть у `prompts.json` плагіна. Код лише підставляє плейсхолдери. Новий плагін = новий `prompts.json` + новий канонічний сценарій. Нуль змін у Python.
5. **Розділення шарів контексту.** System (персона + правила) / Glossary (термінологія) / Scene (де і що) / Surrounding (сусідні рядки) / Per-string (хто + текст). Кожен шар має своє місце і свій бюджет токенів.

## 2. Карта поточної системи (як є зараз)

### 2.1 Підготовка сценарію — три воркери

| Етап | Файл | Що робить | Куди пише |
|---|---|---|---|
| **A. Pre-Analyzer** (видобуток персонажів/термінів) | [core/mempalace/script_analyzer.py](../core/mempalace/script_analyzer.py) | Читає вступ сценарію (перші 2000 рядків `.txt`, або весь `.md` локально), ШІ видобуває персонажів (`gender`, `age_group`, `relationship_summary`, `address_type`, `description`), предмети/терміни, соціальні зв'язки | Glossary (`.md`) + SQLite: `Global_Cast_Profiles`, `knowledge_graph` |
| **B. Chapter Mapper** (хронологія + прив'язка) | [core/mempalace/chapter_mapper.py](../core/mempalace/chapter_mapper.py) | Сегментує сценарій на розділи (start/end line), прив'язує кожен ігровий рядок (BMG) до рядка сценарію | SQLite: `script_chapters`, `script_mappings` |
| **C. Context Weaver** (опис сцен) | [core/mempalace/weaver_worker.py](../core/mempalace/weaver_worker.py) | Плете BMG-рядки в хронологічну послідовність сцен; (опц.) ШІ генерує `visual_scene_context` на кожну сцену + `speaker_map` | SQLite: `drawers` (`visual_scene_context`), `rooms` |

Сховище контексту — локальний SQLite `mempalace_local.db` (див. [core/mempalace_client.py](../core/mempalace_client.py)). Схема: `wings` (гра) → `rooms` (сцени) → `drawers` (контент сцени) + `knowledge_graph` (стосунки) + `script_chapters`/`script_mappings` (хронологія).

### 2.2 Збірка промпту під час перекладу

Усе сходиться в [handlers/translation/ai_prompt_composer.py](../handlers/translation/ai_prompt_composer.py), метод `compose_batch_request` (пакетний переклад) і `compose_messages` (одиничний/варіації). Послідовність:

1. **Спікер на рядок** — резолвиться каскадом: кеш контексту (`get_cached_context` за `BMG_id`) → прямий мапінг сценарію (`ScriptSpeakerFinder.find_speaker_in_script`) → переклад імені через глосарій. Односливні рядки → `speaker = "NONE"`.
2. **Сцена на чанк** — `room` з кешу → `get_room_visual_context` (візуальний опис) + релевантні `relations` (для ти/ви) → плюс «Surrounding Dialogue» (±3 рядки з перекладами).
3. **Глосарій** — `get_relevant_terms` по тексту чанку **+ lookahead на 60 рядків уперед** + записи глосарія для імен спікерів.
4. **JSON payload** — `{ strings_to_translate: [{id, text, speaker, scene_context?}], scene_context, glossary }` + масив `instructions` (зараз **захардкоджений** у коді) + `system_prompt` (з `prompts.json`).

```
┌─ SYSTEM (prompts.json: translation.system_prompt) ── персона + 11 правил
│
└─ USER ─┬─ Game / Mode / Block
         ├─ INSTRUCTIONS (хардкод у ai_prompt_composer.py)   ← портативна діра №1
         └─ JSON DATA
              ├─ strings_to_translate: [{id, text, speaker}]
              ├─ scene_context  (room + visual + relations + surrounding)
              └─ glossary       (markdown-таблиця Original|Translation|Notes)
```

### 2.3 Провайдери

[core/translation/providers.py](../core/translation/providers.py). `GeminiProvider` працює, але **нативний виклик субоптимальний** (див. §6):
- `_translate_via_native_api` **склеює** system+user в один `user`-блок (`full_prompt = system\n\nuser`) — Gemini не отримує `systemInstruction` окремо.
- У `generationConfig` передається **тільки `temperature`** — немає `responseMimeType: application/json`, немає `responseSchema`, немає `thinkingConfig`.

## 3. Модель шарів контексту (формалізація)

Кожен переклад збирається з п'яти шарів. Це контракт: новий плагін наповнює ті самі шари.

| Шар | Призначення | Джерело | Кешується між рядками? |
|---|---|---|---|
| **L1 System / Persona** | Хто перекладач, тон гри, тверді правила (теги, формат, ти/ви, глосарій-пріоритет) | `prompts.json → translation.system_prompt` | ✅ незмінний → ідеальний кандидат на context caching |
| **L2 Glossary** | Канонічні переклади термінів та профілі спікерів (стать/вік/звертання) | GlossaryManager + lookahead | ⚠️ змінюється повільно (на чанк) |
| **L3 Scene** | Локація, що відбувається візуально, стосунки активних персонажів | SQLite `visual_scene_context` + `knowledge_graph` | ⚠️ на сцену |
| **L4 Surrounding** | ±K сусідніх рядків (оригінал + поточний переклад) для зв'язності | data_store + поточні переклади | ❌ на рядок |
| **L5 Per-string** | `{id, text, speaker}` — те, що реально перекладаємо | resolver спікера | ❌ на рядок |

> **Правило бюджету:** L1 завжди повний. L2/L3 — релевантна вибірка, не весь глосарій. L4 — K=3 за замовчуванням. Зростання L5 (розмір чанку) має балансуватися з L2+L3, щоб не розмивати увагу моделі.

## 4. Канонічний формат сценарію (ключ до масштабованості)

Це **серце стратегії**. Зараз `.txt`-шлях тримається на евристиках (спікер = рядок у ВЕРХНЬОМУ РЕГІСТРІ, нечіткий пошук тексту). `.md`-шлях ([core/markdown_script_parser.py](../core/markdown_script_parser.py)) уже детермінований — але формат ніде формально не описаний. Описуємо його як **Picoripi Script Markdown (PSM) v1** і робимо обов'язковим вхідним артефактом для будь-якого нового плагіна.

### 4.1 Схема PSM v1

````markdown
# Synopsis
Короткий переказ сюжету гри (1–3 абзаци). Дає L1/L3 загальний фон.

# Characters
- **LINK** (Translation: `Лінк`)
  - **Gender**: male
  - **Age**: child
  - **Relationship**: головний герой; вихованець села Ордон
  - **Address style**: до старших — шанобливо ('ти'); рівних — на 'ти'
  - **Description**: мовчазний, але рішучий пастух, обраний духами.
- **RUSL** (Translation: `Русль`)
  - **Gender**: male
  - **Age**: adult
  - **Relationship**: наставник Лінка, чоловік Улі
  - **Address style**: до Лінка неформально ('ти')
  - **Description**: хоробрий мечник із Ордону.

# Terms
- **Ordon Shield** (Original: `Ordon Shield`)
  - **Translation**: `Ордонський щит`
  - **Description**: дерев'яний щит, виготовлений Руслем.

# Timeline

## Chapter 1: Ordon Village
### Location: Ordon Village
{Action: Ранок. Лінк зустрічає Русля біля струмка.}
RUSL: Hey, Link. Got a minute?
LINK: ...
{Action: Русль простягає щит.}
RUSL: Take this shield to Hyrule Castle.
````

### 4.2 Чому саме так

- **Прямі прив'язки.** `SPEAKER: text` — детермінований спікер, без вгадування за регістром.
- **`{Action: ...}`** → це і є L3 (візуальний контекст сцени) без окремого ШІ-проходу. ШІ-генерація опису сцени стає *необов'язковим покращенням*, а не критичним етапом.
- **`### Location:`** → `room` (сцена) детерміновано; хронологія = порядок розділів.
- **Профілі персонажів** із явними `Gender/Age/Address` → прямо лягають у глосарій і в `knowledge_graph` без ШІ-видобутку (етап A стає локальним парсингом, як уже реалізовано для `.md`).
- **Портативність.** Будь-яка гра, будь-який walkthrough зводиться до цього формату. Код не змінюється — змінюється лише `.md`.

### 4.3 Підготовка сирого walkthrough → PSM (новий етап «0»)

Більшість walkthrough'ів — це вільний `.txt`. Пропонується **одноразовий конвертер**, керований ШІ (окремий від рантайму перекладу):

```
raw_walkthrough.txt ──> [PSM Converter (ШІ, чанками)] ──> game_script.md (PSM v1)
                              │
                              └─ промпт «structure-extraction»: розбий на Synopsis/Characters/Terms/Timeline,
                                 познач спікерів як SPEAKER:, події як {Action:}, локації як ### Location:
```

Це переносить усю «брудну» роботу в один контрольований крок із людською перевіркою результату. Після нього всі три воркери (A/B/C) працюють детерміновано на чистому `.md`.

> **Рекомендація:** додати цей конвертер як майстер у `ui/mempalace_builder_dialog.py` («Крок 0: Підготувати сценарій») з промптом у `prompts.json → mempalace.psm_conversion_*`. Результат користувач переглядає і править вручну перед етапами A/B/C.

## 5. Промпти: що, де і як замінювати

### 5.1 Карта розташування

| Промпт | Зараз | Має бути |
|---|---|---|
| Системний (переклад) | `prompts.json → translation.system_prompt` ✅ | без змін |
| **Інструкції на запит** (batch/variation) | **захардкоджено** в `ai_prompt_composer.py` ❌ | винести в `prompts.json → translation.instructions_batch` / `instructions_single` |
| Mining / Synthesis / New term | `prompts.json → mempalace.*` (з fallback у коді) ✅ | без змін; додати `psm_conversion_*` |
| Глосарій (creative) | `prompts.json → glossary.prompt_template` ✅ | без змін |

**Портативна діра №1** — масив `instructions` у `compose_batch_request` (рядки ~501–527) і `compose_messages` (~730–737) захардкоджений. Для нового плагіна його не можна змінити без правки Python. **Рекомендація:** перенести в `prompts.json`, лишивши поточні значення як вбудований fallback (так само, як зроблено для `mempalace.*`).

### 5.2 Цільовий системний промпт (оптимізований під Gemini 3 Flash)

Поточний промпт (`zelda_mc/prompts.json`) — добрий, але «правилоцентричний». Gemini Flash краще реагує на **роль + явну ієрархію пріоритетів + few-shot**. Пропонована структура (зберігає всі наявні правила, додає каркас):

```markdown
# Роль
Ти — українська локалізаційна студія рівня Nintendo, що адаптує «{{GAME_NAME}}».
Твоя ціль — не дослівний переклад, а жива художня адаптація, яка звучить природно українською.

# Ієрархія пріоритетів (від найвищого)
1. ГЛОСАРІЙ — переклади термінів точно як у колонці Translation. Можна лише відмінювати.
2. ТЕГИ І ФОРМАТ — усі {...}, [...], \n копіюються без змін; кількість рядків незмінна.
3. КОНТЕКСТ СЦЕНИ — speaker, scene_context і relations визначають тон, стать і ти/ви.
4. ХУДОЖНІСТЬ — переставляй слова, додавай епітети, уникай калькування.

# Тверді правила
- Багаторядковий текст (\n) — це одна думка. Перекладай як цілісну фразу.
- Не перекладай вміст тегів. [Color:Red] — правильно; [Колір:Червоний] — ні.
- Узгодження роду/числа за статтю мовця і слухача (я мав/я мала).
- Звертання та вигуки — варіативно за характером персонажа (не завжди 'гей', 'друже').

# Приклади
Вхід:  "Southern\nFairy Island"
Вихід: "Південний\nОстрів Фей"   (єдина назва, не "Південний\nФея Острів")

Вхід (speaker=RUSL→LINK, relation=наставник→учень): "Hey, kid. Take care."
Вихід: "Гей, малий. Бережи себе."   (неформально, бо наставник до учня)
```

Ключові зміни проти поточного: (1) явна **ієрархія пріоритетів** замість плаского списку; (2) **few-shot приклади** (Gemini Flash на них дуже добре реагує); (3) роль винесена нагору. Усі наявні 11 правил зберігаються — просто перегруповані.

## 6. Оптимізація під Gemini 3 Flash (зміни у providers.py)

Це найбільший технічний важіль якості/вартості. Поточний `GeminiProvider._translate_via_native_api` недовикористовує API.

### 6.1 Окремий `systemInstruction`

Зараз: `full_prompt = system + "\n\n" + user` → усе як один user-блок. Gemini обробляє системну інструкцію інакше і надає їй більшої ваги, коли вона в окремому полі.

```python
body = {
    "systemInstruction": {"parts": [{"text": system_prompt}]},
    "contents": [{"role": "user", "parts": [{"text": user_prompt}]}],
    "generationConfig": {...},
}
```

### 6.2 Гарантований JSON (структурований вивід)

Зараз результат парситься через `robust_json_loads` (зачистка ```json```, пошук `{...}`). Для пакетного перекладу це крихко. Gemini підтримує:

```python
"generationConfig": {
    "temperature": 0.7,
    "responseMimeType": "application/json",
    "responseSchema": {                       # для batch-перекладу
        "type": "object",
        "properties": {
            "translated_strings": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "id": {"type": "integer"},
                        "translation": {"type": "string"}
                    },
                    "required": ["id", "translation"]
                }
            }
        },
        "required": ["translated_strings"]
    }
}
```

Це усуває цілий клас retry'їв «previous response was invalid».

### 6.3 thinkingConfig (Flash)

Для Flash-моделей із режимом мислення — керувати бюджетом: для перекладу зазвичай достатньо низького/нульового thinking (швидше, дешевше), для складних сцен можна підняти. Винести в налаштування провайдера.

### 6.4 Context caching для L1/L2

Системний промпт (L1) однаковий на весь сеанс перекладу. Глосарій (L2) змінюється повільно. Кешування префікса контексту (explicit/implicit caching Gemini) суттєво здешевлює пакетний переклад тисяч рядків. **Рекомендація:** структурувати запит так, щоб незмінний префікс (L1 + повний глосарій) ішов першим і кешувався, а змінна частина (L3–L5) — у кінці.

> Звірити актуальні назви полів API і ліміти перед імплементацією через `/claude-api` чи документацію Gemini — синтаксис вище ілюстративний.

## 7. Контракт плагіна (що надає кожен новий плагін)

Щоб додати нову гру, автор плагіна постачає рівно це:

```
plugins/<game>/
├── translation_prompts/
│   └── prompts.json          # L1 system + (нове) instructions_batch/single + mempalace.*
├── game_script.md            # PSM v1 — канонічний сценарій (єдине справжнє джерело контексту)
└── glossary.md               # (генерується етапом A, але можна заздалегідь засіяти ключові терміни)
```

Плюс у `game_rules` плагіна:
- `get_default_script_name()` → `"game_script.md"`
- `get_dynamic_name_tags()` → підстановки тегів імен (напр. `{LINK}` → ім'я гравця)
- `get_display_name()` → ім'я wing у SQLite

**Усе. Жодного Python-коду перекладу писати не треба.** Код читає `prompts.json` і `game_script.md`; решта виводиться детерміновано.
