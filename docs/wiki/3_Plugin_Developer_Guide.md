# Plugin Developer Guide

**Language:** English · [Українська](uk/3_Plugin_Developer_Guide.md)

A plugin teaches Picoripi one game or text format: how to read and write its files, what its tags are, how wide a line may be, and — optionally — what the game's own data says about each line. This page is the only plugin guide. The list of every hook is generated from the code: [docs/PLUGIN_CONTRACT.md](../PLUGIN_CONTRACT.md).

Source of truth: `plugins/base_game_rules.py` (the hooks and their defaults), `plugins/spec.py` (the contract as data), `ui/main_window/main_window_plugin_handler.py` (loading), `ui/settings/logging_mixin.py` → `find_plugins` (discovery).

---

## Start a plugin

```powershell
.\venv\Scripts\python.exe tools/new_plugin.py <id> "<Display Name>" --prefix XX
```

`<id>` is the folder name under `plugins/`; `--prefix` is the short uppercase tag of the plugin's problem ids (`XX_WIDTH_EXCEEDED`). The command copies `plugins/default_plugin`, renames the prefix and the display name, and writes `tests/test_plugins/test_<id>/test_rules.py` with three passing checks (the plugin loads, a sample survives load and save, the validator passes). The application lists the new plugin at once.

Then, in this order:

1. Parsing: `load_data_from_json_obj` / `save_data_to_json_obj` in `rules.py`. Put a real sample into `SAMPLE` in the generated test before touching anything else.
2. Tags: `tag_manager.py`.
3. Widths: `fonts/*.json`, `font_map.json`, the limits in `config.json`.
4. Prompts: `translation_prompts/prompts.json`, last.

Check and test:

```powershell
$env:PYTHONPATH = "."; .\venv\Scripts\python.exe -m plugins.validate <id>
$env:PYTHONPATH = "."; .\venv\Scripts\python.exe -m pytest -n auto tests/test_plugins/test_<id>/
```

`python -m plugins.validate` calls every hook with dummy arguments and reports a hook that raises, a wrong return type, a signature the host cannot call, a broken JSON file, per-session keys in `config.json`, and (as warnings) main-window attributes outside the allowed list.

### Collect before coding

The exact file format with sample source and translated files and the expected save output; the maximum width and lines per page; every tag and control code, which are zero-width and how wide the visible ones are; where font metrics come from; how pages break; speaker or chapter metadata; whether unknown fields must round-trip unchanged. `plugins/default_plugin/AI_PLUGIN_ASSISTANT_PROMPT.md` asks these questions in a form you can paste to an AI assistant.

## Discovery and load

**Discovery** (New Project and Settings → Global → Active Game Plugin): every directory under `plugins/` that contains `config.json`, except `import_plugins`. `display_name` in that file is the label and must be unique; the folder name is the plugin id.

**Load:** `importlib.import_module(f"plugins.{id}.rules")`. The module must define `GameRules`, a subclass of `BaseGameRules`, constructed as `GameRules(main_window_ref=self.mw)`. It must also build without a main window (`GameRules()`): tests and the validator do that. No network, disk-heavy or archive work in `__init__`.

If the import fails, the user gets **Plugin Load Error** and the application falls back to `BaseGameRules`. Switching plugins drops every loaded module of the plugin, so module-level caches start empty.

**Aliases:** after load, `plugins/<id>/aliases.json` (shipped defaults, read-only) and then the user's own `aliases.json` from the per-user plugin folder are merged into `default_tag_mappings`. The application saves aliases only to the per-user folder.

**Force aliases and names drawn in colour:** an alias whose name starts with `F:` (`"{F:Link}": "{Player}"`) reaches the model as the plain word, which it declines; the translation keeps that word and not the tag, so a renamed hero still reads «Лінк». If the game itself draws that name in a colour, return the colour tags from `get_force_alias_wrapping()` (`{"{F:Link}": ("{Color:Green}", "{Color:White}")}` in Minish Cap): the word is sent wrapped and the declined form comes back in the same colour; the tag warning does not count those tags as extra. Find out per game whether the engine colours the name — Twilight Princess, The Wind Waker and Tears of the Kingdom do not (TotK: none of the 76–99 `{playerName}` tags per language has a colour tag around it; English writes "Link" as plain text; Wind Waker HD: 326 of 359 `[Name]` tags stand in no colour at all; Skyward Sword HD: 626 of 631 `{heroName}`), Minish Cap does.

**Menu actions:** `get_plugin_actions()` may add `QAction`s (`name`, `text`, `tooltip`, `shortcut`, `handler`, `menu`, `toolbar`). The AI translate actions belong to the application and are present for every game.

## Files of a plugin

```
plugins/<id>/
  config.json                         # required: at least "display_name"
  rules.py                            # required: class GameRules(BaseGameRules)
  config.py                           # problem ids and default detection / autofix settings
  tag_manager.py                      # the game's tags and their highlighting
  font_map.json, fonts/*.json         # widths
  font_sources.json                   # the game's fonts for the font editor (optional)
  texture_sources.json                # the game's textures with text for the Textures window (optional)
  translation_prompts/prompts.json    # prompt sections the game changes
```

**`config.json`** — defaults for a new project: `display_name`, `game_dialog_max_width_pixels`, `line_width_warning_threshold_pixels`, `width_tolerance_percent` (how far past the target width a line may go before it must be shortened; used when a window kind gives only one width), `lines_per_page`, `default_font_file`, `detection_enabled`, `autofix_enabled`, colours and wrap flags. Per-session keys (open file paths, selection, scroll positions, search history) are refused by the validator; the application stores those in `project_settings.json`.

**`config.py`** — `PROBLEM_DEFINITIONS, DEFAULT_DETECTION_SETTINGS, DEFAULT_AUTOFIX_SETTINGS = generate_base_config(PREFIX, overrides=…, custom_problems=…)` from `plugins/common/config_factory.py`.

**`rules.py`** — `GameRules` declares its parts with class attributes and `BaseGameRules` wires them:

```python
class GameRules(BaseGameRules):
    problem_prefix = "XX"
    problem_definitions = PROBLEM_DEFINITIONS
    tag_manager_class = TagManager        # default: GenericTagManager
    tag_style = "curly"                   # "square" when tags look [like this]
    analyze_whole_string_first = True
```

With these the base class builds the tag manager, the problem analyzer and the text fixer and answers the hooks that only pass a call on (problem definitions, highlighting, analysis, autofix, short problem names). Name `problem_analyzer_class` / `text_fixer_class` only for game-specific checks or fixes (subclass `GenericProblemAnalyzer` / `GenericTextFixer` from `plugins/common/`). `problem_ids = problem_ids(DEFINITIONS, PREFIX, without=(…))` leaves out standard checks the game does not use.

**String context for a check.** While the host checks one string, the analyzer's `_current_scan_block_idx` and `_current_scan_string_idx` hold that string's block and string index. The host sets them around each analysis and restores the previous values after. The values are per thread: a thread sees only the values it set, so two threads that check strings with one analyzer do not mix them. Outside a string analysis both are `None`; read them with `getattr(self, "_current_scan_block_idx", None)` and handle `None`. Do not keep them after the call. For a detail under a problem's name in the editor tooltip, implement `get_problem_detail(block_idx, string_idx, problem_id)`. Return a short text, or `""` for no detail.

**`font_map.json` and `fonts/*.json`** — `fonts/*.json` are font maps (`{character: {"width": N}}`). The root `font_map.json` overrides widths of visible tags and icons: `{"[A]": {"width": 16}, "{COLOR_RED}": {"width": 0}}`. A visible icon tag is not zero-width. Widths the user sets in the application (tag width dialog, Settings → font map) are saved to `~/.picoripi/plugins/<plugin>/font_map.json`, which wins over the plugin's file; the same holds for `translation_map.json` written by the BFN editor without a project and `window_layouts.json` written by the Settings table of per-window limits. The application never writes into `plugins/`.

plain 8-bit, 4-bit and 24-bit ZSoft PCX are read too), `m2` (every texture of an M2 PSB file: RGBA8 stored B, G, R, A, A8L8, A8, L8; written in place), `g4tx` (Level-5 Switch G4TX texture set: NXTCH textures, RGBA8, BC1, BC3, BC7), `shpg` (EA SHPG shapes of the Wii: C4/C8 with a palette, RGB5A3, RGBA8, CMPR), `bfres` (the FTEX textures of a Wii U BFRES file, e.g. Paper Mario: Color Splash UI pictures; cube maps and SNORM textures are left out), `mibl` (Monolith Soft MIBL textures of the Switch Xenoblade games, `.witex`), `ctrt` (Kingdom Hearts 3D `.ctt` pictures: a 0x80-byte header and one PICA texture), `l2d` (the CTRT pictures kept inside a Kingdom Hearts 3D `.l2d` layout), `wilay` (the MIBL textures of a Xenoblade `.wilay` layout, written back in place, and the JPEG of a tutorial picture layout), `ctxr` (MGS2 / MGS3 Master Collection `.ctxr`: the Switch NVN texture and the PC TXTR version 7), `phyre` (a PhyreEngine `.NXGL.phyre` file with one texture, Dragon Quest Builders 1: ARGB8, ARGB4444, DXT1 or DXT5, bottom-up rows, mip levels written again; a pack of many textures, the Builders 1 `uitex`/`uiicon` sprite packs, is read too: the format names in use and the fix-up groups give each texture's format), `is_tex` (Infinite Space `.tex` 3D textures with their palette), `dq9_spr` (Dragon Quest IX `.spr` pictures), `jade` (Jade engine textures of Rayman Raving Rabbids 1/2 as `.jtex`: 4/8-bit with a palette, TGA RGBA8, DDS DXT1/3/5; an edited 4/8-bit picture takes the nearest palette colours), `jade_jtx` (Jade Montreal JTX textures of TV Party as `.jtx`: DXT1, DXT1 + alpha, C4/C8 with a palette, BGRA8; mips written again), `raw` (headerless pixels at known offsets, e.g. N64 textures: `params.pixel_format` such as `n64:IA8` or `snes:2bpp` / `snes:3bpp` / `snes:4bpp` (SNES planar 8x8 tiles, colour indices shown as grey; `3bpp` is A Link to the Past's layout), `width`, `height`, and `offset` or a list `textures` of `{name, offset}`; `n64:CI4`/`CI8` and `psx:CI4`/`CI8` index a palette at `tlut_offset`, `psx:RGB555` is PlayStation 16-bit, `psx:4bpp`/`8bpp` indices without a CLUT, `saturn:1bpp_12x12` 1-bit 12x12 glyphs one after another), `vs_gim`, `vs_hf1`, `vs_rle` (Vagrant Story screen tile maps, help-page sprites (`params.sprites`) and the RLE title screen (`offset`, `end`, `width`, `height`, `textures` rectangles); a picture that no longer compresses into its place is refused), `sotn_blocks` / `sotn_cmp` (Symphony of the Night PlayStation pictures: the 128x128 VRAM tile blocks of the `F_*.BIN` files, `bpp`, `blocks`, `clut` or `palette`; an image packed with the game's nibble coder at `offset`, `width`, `height`, `room`, packed again on save and refused when it no longer fits), `sh3_tex` (Silent Hill 3 PC `pic.arc` textures: PS2 GS 8-bit with a palette and 32-bit RGBA; other header kinds are not read yet), `mt_tex` (Capcom MT Framework 3DS `TEX`: one PICA picture with its mip levels, Monster Hunter), `pmd_img` (Spike Chunsoft 3DS `.img` pictures of Pokémon Mystery Dungeon: Gates to Infinity and Super Mystery Dungeon: a 128-byte `\0cte` header and one PICA surface stored bottom row first; RGB8, RGBA8, RGBA4, ETC1, ETC1A4, A8), `ffta2_efx` (the DS 3D textures of Final Fantasy Tactics A2 `*.efx` effect files: A3I5 / A5I3 with their own palette; a changed texel takes the nearest palette colour), `tiles` (GBA / DS / Saturn 8x8 character tiles of 1-, 4- or 8-bit palette indices, shown as grey levels: an NCGR takes its size from its header; headerless tiles take `bpp`, `offset`, `tiles`, sprite cells `cell` `[w, h]` in tiles and `per_row`; colours: `palette` (the game's BGR555 bytes as hex), `bank` and `banks` (one hex digit per tile, `.` = `bank`); `nibble: "high"`: the first pixel of a 4-bit byte is its high nibble (Saturn); 1-bit tiles are 8 bytes, the first pixel in the high bit; `linear`: a plain bitmap of `per_row` x 8 pixels a row instead of tiles, an imported off-palette colour takes the nearest colour of the tile's bank), `tilemap` (a pattern name map over a bank of 8x8 cells of 4- or 8-bit indices, shown as one picture per map: Saturn VDP2 screens such as the Symphony of the Night title and menu screens; `map_offset`, `cols`, `rows`, `cells_offset`, `bpp`, `nibble`, `unit` (bytes per cell number), `name_mask`, `pal_shift` / `pal_mask` (the palette number in the name), `hflip_bit` / `vflip_bit`, `blank`, `palette`, `max_tiles` and `textures` for several screens over one bank; a redrawn block reuses an equal cell, is redrawn in place when only its map entry uses the cell, else takes a free cell or grows the bank up to `max_tiles`)), `path` (as in `font_sources.json`; `{a,b}` alternatives allowed; the folder part may hold a glob too, `data/map/*/*_en.xc`), optional `member` (a glob inside the archive at `path`; archives inside archives are walked — `Title.szs/timg/*.bflim`; an N64 ROM's dmadata files are `#<index>`; Grezzo ZAR/GAR archives are archives too) and `params`: `compression` of the member (or of the file when there is no member: `zlib`, `gzip`, `yar`; Yaz0, zstd and Grezzo LzS are found by their magic), `file_offset` + `file_size` (the texture file is that byte range, for packs indexed elsewhere) and `texture` (a glob of texture names in a file that holds several). The pixel format comes from the file itself; the code in `core/texture_formats/` holds no game constants. A texture keeps its size; only the 4x4 blocks or tiles that changed are encoded again, so an unedited texture writes back byte for byte. A file that holds both text and pictures (a program with its title screen) keeps the edited pictures when the text is saved: the host carries them from the translation copy into the rebuilt file.

**`translation_prompts/prompts.json`** — may hold only the sections the game changes (usually `translation`); the rest is merged in key by key from `plugins/common/defaults/prompts.json`. Never add an instruction that permits changing tags.

## File formats and the state that goes with them

`get_file_formats()` returns `core.formats.FileFormat(extensions, mode, label)` items. `mode` is the shape in which a file's content reaches `load_data_from_json_obj` and leaves `save_data_to_json_obj`: `"json"` (parsed), `"text"` (a string) or `"bytes"`. The default is `.json` + `.txt`. A game with its own table returns `[FileFormat((".tbl",), "bytes", "Text tables"), *DEFAULT_FORMATS]` and parses the bytes itself; project import, loading, saving and the open/save dialogs follow without host changes. An archive format is added with `ContainerManager.register(MyContainer, extensions=(".pak",))`.

`includes_source_file(rel_path)` decides whether a source file becomes a block. `rel_path` is relative to the source folder and uses `/`. The default is `True`. A game whose unpacked tree holds the same text in many languages returns `True` only for the language it translates. The other files stay in the source folder: a build can still read them, and `load_multi_reference` can show them as reference columns. A block whose file the hook refuses leaves the project list at the next sync; its translation file stays on disk.

`unpack_reference(path, project_dir, progress, is_cancelled)` reads a reference the user picked as a file (a game image of another region). The host calls it on a worker thread. The plugin writes what `load_multi_reference` needs into a folder of the project and returns that folder; the host stores the folder as the reference path. Return `None` to use the path as it is (the default). Write into a temporary sibling and rename it into place, so a cancel leaves the older folder. `load_multi_reference` then reads only that folder: it runs on the UI thread and must stay fast. Example: `plugins/super_mario_sunshine/reference.py` writes only the BMG files of the European disc.

Inside the application the text is `List[List[str]]` — blocks of strings — plus block names. `load_data_from_json_obj` returns `(blocks, block_names)`; `save_data_to_json_obj(blocks, block_names)` returns what goes back to the file. Unknown fields of the format must survive the round trip.

If saving needs something the strings do not carry (table keys, the parsed binary file), keep it in the plugin and implement `export_runtime_state()` / `restore_runtime_state(state)` / `reset_runtime_state()` — plain JSON data that the host keeps across reloads, reverts and sessions — and `prepare_save_context(context)`, called before each project file is built (`context.block_indices`, `context.runtime_state`, `context.existing_versions()` yields the file's current bytes, translation first). A session written before the plugin kept any state restores none: the host then reads the project files once on a worker for the state only (the restored strings and edits stay) and scans the issues again. The host never reads plugin attributes. Examples: `plugins/pokemon_fr/rules.py` (keys), `plugins/manual_3ds/rules.py` (one manual per block), `plugins/zelda_bmg/rules.py` (a binary file patched on save).

## Capabilities and the game's own data

Everything above is the required minimum. Beyond it a plugin can mine the game's own data — message attributes, dialogue graphs, scene tables — or an outside lore source, and feed that into AI translation, glossary building and the Story Timeline. All of it is opt-in; every hook has a safe default.

| If you have | What becomes possible |
|---|---|
| A decompilation or the game's source | window kinds, dialogue flow, scene tables, actor placement |
| Raw game files (message archives, stage data) | the same, by parsing the binaries |
| A community wiki | lore lookup for glossary descriptions |
| A fan script or walkthrough | scene and speaker structure for MemPalace |
| Only the extracted text | nothing here is needed — the text sweep still builds a glossary |

`get_capabilities() -> Set[str]` tells the Localization Pipeline which steps to offer. Declaring nothing is a complete answer.

| Name | Hook it promises | What appears |
|---|---|---|
| `glossary_seed` | `get_glossary_seed_entries()` | Glossary terms taken from game data without an AI request (`term`, `description`, `section`, `icon`, `source_ref`, `blocks`) |
| `external_lore` | `get_external_lore(term)` | Outside knowledge for glossary descriptions |
| `speaker_attribution` | `get_speaker_for_string()` | The **Name the speakers** step and the Speaker field |
| `message_window_preview` | `get_preview_window_style()` and the `get_window_*` hooks | In-game message windows in the preview, per-window limits in Settings |
| `strict_tags` | — | An AI reply that loses, adds or changes a `{tag}` of its source is refused and asked again (games whose control codes all matter) |

Do not declare a capability the plugin cannot deliver.

**Slots, not values.** `get_translation_context_for_string` returns metadata under keys the engine publishes — `window_type`, `content_role`, `role_instruction`, `has_speaker`, `glossary_section`, `force_glossary`, `layout_class` (`"prose"`: Picoripi breaks the lines of each page itself; `"lines"`: one source line is one output line — menus, names, choices; omitted: guessed from the source text). The values are the plugin's: `content_role` may be `"BossName"` or anything the game needs, and `role_instruction` is the sentence that tells the model what the role means. The engine never compares a value to a specific game, and engine code must not learn one.

**Speakers.** `get_speaker_for_string` returns the identity the game data records; the engine fills rows the user has not set and never overwrites a user's choice. `is_placeholder_speaker(name)` says whether that identity is an internal id the script-merge step may replace with a real name (default: yes).

**Message windows.** With `message_window_preview`: `get_preview_window_style(block_idx, string_idx)` gives the style of a message; `get_window_presets()` / `get_window_preset_label()` / `get_window_style_for_preset()` feed the bar that forces a window kind; `get_window_frame(style)` returns geometry and picture read from the game's files; `get_window_item_icon()` and `get_window_text_offset_y()` cover the item slot and the game's vertical centring; `get_window_layout_groups()` / `get_window_layouts_document()` / `save_window_layouts_document()` drive the Settings table of per-window limits. `get_string_layout(block, string)` gives per-string width, font and lines per page (priority: per-string override > this hook > global settings). `fit_text_to_window(text, block, string)` returns a translation re-wrapped with the game's own line and page codes (None: the generic wrapping); the AI translation uses it when it applies a reply, and a plugin may call it from its Autofix. A font source with `"preview": true` is read from the project's own files: the host measures widths with it (its `font_map` name, unless the font editor wrote one) and draws the bitmap preview with its glyphs, for any format in `core/font_formats`.

**Custom preview.** `get_custom_preview_widget(main_window)` returns a `QWidget` that draws the current text in the game's own viewer, in place of the BFN preview; `None` keeps the BFN preview. The host docks the widget in the preview column, hides the BFN preview, calls `refresh()` after each selection change and text edit, and calls `shutdown()` before it deletes the widget. Read the project through `main_window`; the widget must not write to it. `plugins/manual_3ds/preview_panel.py` is the reference.

**MSBT tag names from MSBT Editor.** `plugins/common/gcf.py` reads the game configs of AeonSake's MSBT Editor (`.gcf`) and lays their names, descriptions and value names over a catalogue of `plugins.common.lms_tags` (`gcf.overlay`); the argument layout stays the one verified against the game's text, and renamed tags keep their old names as aliases (`TagCodec(..., aliases=...)`).

**Reference implementation.** `plugins/zelda_bmg/` (Twilight Princess) reads the game's files and a decompilation: message attributes that identify the window and therefore the role of a message (`window_kinds.py`), dialogue flow graphs (`msg_flow.py`), scene tables (`stage_data.py`), per-window layout, a preview with colours, scaling and icons, window frames from a local dump (`window_frame_loader.py`). Copy the approach — find the field in the game's data that already encodes what a message is, and expose it through a hook — not the tables.

## Project Manager: roles, unpacking and build targets

The Project Manager's new-project wizard, its Build, Export and Run buttons and its list icons use six optional hooks.
Each hook has a default, so a plugin without them still works: the wizard then takes the role and the platform from the user, uses the files as they are, and the buttons stay off.

- `get_source_roles()` lists the roles a project's files can have, for example base game, update, DLC and disc 2. The first role is the default.
- `identify_source(path)` reads one file the user added, by its content, and returns its role and platform. It returns `None` for a file that is not from this game.
- `get_platforms()` lists the platforms the game ships on. The wizard uses it when `identify_source` does not name one.
- `unpack_sources(sources, target_dir, progress, is_cancelled)` unpacks the role files into an empty folder that the host made. It returns that folder, or `None` when the files need no unpacking.
- `get_source_subfolder()` names the folder of the unpacked tree that is the project's source root, with `/` separators, for example `files/res/Msgus`. The default is `None`: the whole unpacked folder is the source. The host fails the unpack with a message when that folder is missing. Use it when the unpacked tree holds more than the game's text.
- `unpack_key_consoles()` lists the consoles whose key file the unpack reads: any of `"3ds"`, `"switch"`, `"wii"`. Default: none. The wizard asks for a console's key file only when a chosen file is encrypted and the game lists that console. A game that unpacks no encrypted image returns none.
- Encrypted console images: `core/containers/console_crypto.py`. Inside `unpack_sources`, `key_path(console)` returns the key file the user chose for that console in the wizard, or `None`; the readers in `core/project_library/images.py` read the key file themselves. A reader raises `encrypted_error(console, label)` when the key file or pycryptodome is missing. The plugin never opens a key file itself, and a key path is never written into a project.
- `get_build_targets()` lists what the game can build, each with an `id`, a `label`, `platforms` (empty means all) and a `kind`: `files`, `patch` or `layeredfs`.
- `build_target(target_id, source_dir, translation_dir, output_dir, progress, is_cancelled)` writes one target into an empty output folder and returns the result path.
- `project_icon(project_dir)` returns a PNG or JPEG picture of the game for the project's row, or `None`. The host scales it to 128 px and caches it. It runs in the scan process, so it may read files but must not create widgets. A user's `icon.png` beside the project file wins over it. `plugins/plain_text/rules.py` returns a `banner.png` beside the project file as the example.

These hooks run on a worker thread, except `project_icon`, which runs in the scan process. They must not create widgets or read `self.mw`. The host passes `progress` and `is_cancelled`; check `is_cancelled()` in long loops. The host builds into a temporary folder and renames it when the build succeeds. Export copies the built folder to a folder the user chooses. Run starts the emulator command the user set in the Project Manager, with the built path as an argument.

`plugins/plain_text/rules.py` is the reference: its single target copies the translation files as they are.

Game images: `core/project_library/images.py` reads GameCube discs (NKit GameCube discs too) and Nintendo DS cartridges by their header. Before unpacking a game image the host checks that the target drive has room for it; a plain file, such as a GBA ROM, is used as it is. Call `identify` or `base_identity(path, game_codes)` in `identify_source`, and `extract(path, target_dir, progress, is_cancelled, select=...)` in `unpack_sources`. The game's `unpack.py` lists the files it keeps, as its zt script did; `plugins/zelda_fsae/` is the short example. `ImageError` means a format the helper does not read; let it reach the host, which shows the message.
## Families of versions (family_plan)

A game sold in several versions (for example GameCube, Wii and Wii U HD) can share one translation. `family_plan(sources, project_dir)` gets the folders or files the user gave and returns a `core.family_projects.model.FamilyPlan`, or `None` when the game has no family (the default). The plugin recognises each source by its content, not by the user's folder name: Twilight Princess uses the message count of its files as a fingerprint (`plugins/zelda_bmg/family.py`). The plan lists the members (`FamilyMember(key, label, path, base, parents)`), the base version, and `read(member_key)`, which returns `(unit_id, text)` pairs.

Core (`core/family_projects/`) links the units of each member to the units of its parents by equal match key (the text by default), stores one translation per shared unit, keeps the differing texts as per-member overrides, and fans the texts back out. A member may link to several parents in order: a member that shares most of its text with a second member links to that one first. Fewer sources than members is valid. The Twilight Princess project builder (`plugins/zelda_bmg/family_project.py`) writes one project. Each unit tree (one message and its linked copies) is one project message, in the folder "Shared" (a base-rooted tree of more than one version), "Shared HD Msguk" (the same for a tree rooted in HD Msguk), or "<label> only" (a tree of one version). `FamilyPlan.shared_files` names the files a member takes from the base member byte for byte (the Wii takes `Fontus/fontres.arc`); `family.py shared` copies them.
The Wind Waker family (GameCube BMG and HD MSBT, `plugins/zelda_ww/family.py`) differs in one way: the tags are written in two syntaxes. `family_tags.py` maps them with the table `family_tag_map.json`, derived from the game files (`python -m plugins.zelda_ww.family_tags derive <bmg folder> <msbt folder>`). Its match key reads both sides in HD syntax and drops colour. The family sets `exact_keys`, so the engine pairs each key with its copies by key (`align_by_key`) and not by order. The project opens with the GameCube plugin (`zelda_tww`), which reads MSBT blocks by their magic; its tag highlighting still uses GameCube syntax. The command line: `python -m plugins.zelda_ww.family plan|project|push|verify <family.json>`.

## Tests for a plugin

The generated test file is the start. Add, with real data: a sample that parses into the expected blocks; a save round trip that keeps every field; valid and invalid tags; a width warning on a deliberately long line; autofix returning `(str, bool)` without damaging tags. `plugins/testing.py` has the shared checks (`check_loads`, `check_round_trip`, `check_validator`).

## What not to do

- Do not put game dumps, archives or the publisher's assets in a plugin you commit.
- Do not import PyQt5; the application is PyQt6.
- Do not write game-specific behaviour into `plugins/common/` or into the engine. Window kinds, item ids and role names belong to the plugin.
- Do not check for `Mock` objects in plugin code.
- Do not return metadata that cannot be serialised: it ends up in the session file.
- Do not drop or reorder unknown fields of the file format on save.
- Do not copy `zelda_bmg` tables into another game's plugin.
- Do not forget `config.json` — without it the plugin never appears.
