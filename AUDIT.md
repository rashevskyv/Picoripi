## 2. Архітектурні проблеми та рекомендації (Нові виявлені проблеми)

Під час повторного аудиту було виявлено нові проблеми швидкодії, стабільності та архітектури:

### 2.1. Локальні імпорти у критичних гарячих шляхах (loops / paint-related events)
* **Проблема**:
  * У методі `string_needs_translation` (`core/data_state_processor.py`, лінія 85) та `update_edited_data` (лінія 139) локально імпортуються `re` та `datetime`.
  * У методі `_apply_highlights_to_editor` (`ui/updaters/preview_updater.py`, лінія 282) локально імпортується `re` всередині циклу по блоках редактора. При великих текстах це створює помітний оверхед.
  * У циклі побудови глав MemePalace (`ui/updaters/block_list_updater.py`, лінія 636) локально імпортується `re` на кожній ітерації.
* **Рекомендація**: Перенести всі системні імпорти (`re`, `json`, `datetime`) на рівень модуля (вгору відповідних файлів).

### 2.2. Ризик критичного збою (crash) в AI Chat при відсутності сесій у провайдера
* **Проблема**: В `handlers/ai_chat_handler.py` (лінія 130) сесія ініціалізується з параметром `supports_sessions=provider.supports_sessions`. Якщо вибрано провайдер без нативної підтримки сесій (наприклад, деякі OpenAI-сумісні або локальні моделі), метод `ensure_session` повертає `None`. Наступний виклик `state.prepare_request(...)` призведе до помилки `AttributeError` та вильоту програми.
* **Рекомендація**: Для AI Chat локальна історія (sliding window) потрібна завжди, незалежно від нативності сесій на сервері. Слід передавати `supports_sessions=True` при виклику `ensure_session` у чаті.

### 2.3. Відсутність ліміту контексту історії повідомлень у AI Chat
* **Проблема**: У `handlers/ai_chat_handler.py` історія діалогу передається безпосередньо в API AI провайдерів без обмеження кількості повідомлень або токенів. При тривалій роботі з AI Chat це може призводити до надмірних витрат токенів та сповільнення відповідей AI через переповнення контексту.
* **Рекомендація**: Додати механізм "ковзного вікна" (sliding window), що обмежує історію лише останніми N повідомленнями, або запровадити ліміт на сумарну довжину історії.

### 2.4. Розпорошеність розрахунку ширини тексту та плагінів
* **Проблема**: У різних хендлерах (наприклад, `text_analysis_handler.py`, `text_operation_handler.py`, `ui/updaters/preview_updater.py`) використовуються власні обгортки та прямі виклики `calculate_string_width`. Це ускладнює централізовану модифікацію логіки розрахунку чи додавання глобального кешування.
* **Рекомендація**: Консолідувати розрахунки ширини під егідою `TextAnalysisHandler` або `DataStateProcessor` для створення єдиної точки розрахунків з підтримкою специфічних плагінів та шрифтів.

## 4. Настанови для розробки та тестування

### Підказки для розробки
1. Змінювати лише файли, які безпосередньо стосуються поточного завдання.
2. Після будь-якої модифікації коду обов'язково запускати тестування:
   `$env:PYTHONPATH = "."; .\.venv\Scripts\python.exe -m pytest -n auto tests/`
3. Усі зміни повинні супроводжуватися відповідними юніт-тестами.
4. Заборонено видаляти старі фічі або реалізації без повної заміни аналогічним функціоналом.
5. **Обов'язкова ручна верифікація**: Кожна зміна чи нова функція повинна супроводжуватися чіткими та конкретними покроковими інструкціями для користувача, як перевірити її працездатність вручну в інтерфейсі програми. Ці кроки мають бути виведені в повідомленні після завершення та описані у файлі `walkthrough.md`.
